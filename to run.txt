# 13. Why this structure?

The key idea is:

> **Features own their logic.**

Don't do this:

```text
components/
  Button.tsx
  Circuit.tsx
  Chat.tsx
  Histogram.tsx
  Lesson.tsx
  ...
```

with a giant:

```text
pages/
```

Instead:

```text
features/
    quantum-lab/
    learning/
    ai-tutor/
    challenges/
```

Each feature owns its:

```text
components
hooks
services
types
state
```

This becomes extremely useful when the project gets bigger.

# 15. Circuit state architecture

This is something you should design **before coding the lab**.

Represent a circuit as data.

For example:

```typescript
interface QuantumCircuit {
  id: string;
  name: string;
  qubits: number;
  classicalBits: number;
  gates: QuantumGate[];
}

interface QuantumGate {
  id: string;
  type: "H" | "X" | "Y" | "Z" | "CX" | "S" | "T";
  qubits: number[];
  moment: number;
  params?: number[];
}
```

A Bell state becomes:

```json
{
  "qubits": 2,
  "gates": [
    {
      "type": "H",
      "qubits": [0],
      "moment": 0
    },
    {
      "type": "CX",
      "qubits": [0, 1],
      "moment": 1
    }
  ]
}
```

# 18. Backend API contract

Your frontend should not care whether you're using Qiskit, Cirq, or PennyLane internally.

Create a unified API.

For example:

```text
POST /api/simulate
```

Request:

```json
{
  "framework": "qiskit",
  "backend": "aer",
  "circuit": {...},
  "shots": 1024
}
```

Response:

```json
{
  "counts": {
    "00": 512,
    "11": 512
  },
  "probabilities": {
    "00": 0.5,
    "11": 0.5
  },
  "statevector": [...],
  "executionTime": 0.41
}
```

Then later:

```text
Qiskit
PennyLane
Cirq
qBraid
```

can all conform to the same frontend response format.

That keeps your frontend stable even if your backend changes.

# 22. Your final frontend architecture

I'd summarize the entire frontend as:

```text
                         QUANTUM LEARNING PLATFORM
                                  │
             ┌────────────────────┼────────────────────┐
             │                    │                    │
             ▼                    ▼                    ▼
          LEARN                  LAB                PRACTICE
             │                    │                    │
       Lessons/Theory       Circuit Builder       Challenges
             │                    │                    │
       Visualizations       Code Editor            Evaluation
             │                    │                    │
             └────────────────────┼────────────────────┘
                                  │
                                  ▼
                             AI TUTOR
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
                 Explain       Debug         Optimize
                                  │
                                  ▼
                         SIMULATION BACKEND
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
                 Qiskit       PennyLane        Cirq
                                  │
                                  ▼
                           RESULTS ENGINE
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
                Histogram     State Vector   Bloch Sphere
```

The **single most important architectural principle** is this:

> **The circuit should exist as a framework-independent data structure in your frontend. The visual editor, code generator, simulator API, visualizations, and AI tutor should all consume that same circuit state.**

If you get that right, the project becomes modular instead of turning into a giant pile of UI code. And for your SIH demo, I'd spend **~50% of frontend effort on the Quantum Lab**, ~20% on learning, ~15% on AI interaction, and the remaining ~15% on dashboard/progress/polish.
